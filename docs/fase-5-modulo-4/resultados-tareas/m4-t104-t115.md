## Flujo de navegador y aislamiento

`conBaseOperativa` crea una base `citas_m4_test_<uuid>`, aplica todas las migraciones y abre dos conexiones. Siembra dos negocios y los tres roles. Nest usa el DataSource desechable y un reloj inyectado; los JWT corresponden a sesiones persistidas, y las rutas reconstruyen rol y negocio desde el servidor. Vite usa la API escuchando solo en loopback y Edge abre `/admin/agenda` conectado.

Administración y Recepción eligen cliente por ID o crean una persona independiente con el mismo teléfono. El formulario consulta `/disponibilidad` en modalidad manual, prepara la clave y registra mediante las rutas reales. Se comprueban Confirmada, folio, costo, tarjetas de agenda y filas de cliente/cita/evento/intento. El directorio permite crear y corregir una ficha; la corrección no modifica las citas anteriores. El Profesional recibe una cita propia entre fixtures de otro Profesional y otro negocio; consulta contacto/notas sin directorio ni controles de escritura.

Para perder una respuesta, Playwright hace `route.fetch()` y comprueba el 201 real **antes** de abortar la entrega al navegador. El doble clic produce una sola llamada de registro. Tras recargar, «Comprobar envío pendiente» resuelve la misma clave y muestra el folio guardado. Se verifica que existe solo una cita y un evento. Ninguna respuesta exitosa se fabrica con `route.fulfill`.

En móvil y escritorio se confirma con Enter, se abre la tarjeta por teclado, se cancela, reactiva, cambia estado y mueve la cita. El folio se conserva y cada cambio queda en historial. El reloj de servidor se lleva al fin exacto de atención para corregir Completada a No asistió; se conserva la versión y el historial anterior. El directorio también se recorre por teclado, con comprobación de foco, botón visible y ausencia de desbordamiento horizontal.

El cierre libera Edge, Vite, Nest y los pools antes de destruir la base validada. Un caso lanza un fallo deliberado desde el recorrido y luego consulta `information_schema.SCHEMATA` para comprobar que la base propia desapareció. No se escribe en la base cotidiana. Se requieren las dependencias instaladas de `../frontend-saas` y Microsoft Edge; no se necesita un backend cotidiano levantado.

Un recorrido de diagnóstico se interrumpió externamente durante el desarrollo. Ese cierre abrupto no ejecutó todos los `finally`: se identificó su esquema efímero exacto por el inventario y la fecha de creación de sus tablas, se comprobó ausencia de conexiones activas, se eliminó únicamente ese esquema y se verificó su desaparición. La garantía comprobada por el caso automatizado cubre errores normales del recorrido; no se atribuye ejecución de `finally` a una terminación externa del proceso.

## Barreras, cupo y filas finales

Cada carrera usa dos aplicaciones y conexiones diferentes. El primer escritor entra por HTTP y ejecuta su SQL real hasta adquirir el perfil común; la barrera conserva esa transacción abierta. El segundo también entra por la ruta real y se observa mediante `PROCESSLIST`, por ID de conexión, esperando un `FOR UPDATE` de usuarios compartidos antes de alcanzar el perfil. La sesión pública nace mediante la ruta de inicialización, con cookie y CSRF; la manual usa el JWT de su actor. Se comprueba que ambos IDs difieren, se abre la barrera y se esperan ambas respuestas HTTP (201/409, o dos 201 para contigüidad). `finally` abre cualquier barrera pendiente y cierra los recursos aun ante aserciones fallidas. Las comprobaciones secuenciales adicionales usan los servicios reales sobre la misma persistencia.

## Seguridad y fallos

La matriz HTTP comprueba 400/401/403/404/409 y que recurso ajeno equivale a inexistente. Nombre de 151 caracteres, teléfono inválido, notas de 2.001 y campos como `negocioId`, `costo` o `excluirCitaId` se rechazan. Las respuestas personales y errores llevan `Cache-Control: no-store` y no contienen los marcadores de SQL, traza o contacto ajeno inyectados.

El límite de 32 KiB del JSON público conserva su regresión en `src/reservas-publicas/limite-cuerpo-publico.spec.ts`, incluida en las 648 unitarias aprobadas. No se inventa un límite de 32 KiB para las rutas privadas.

Los fallos de lectura se inyectan **después** de ejecutar la consulta real de citas o clientes: inesperado produce 500 y timeout produce 503. No hay colección parcial ni 200 vacío. Retirar el fallo permite reintentar y recibir el resultado real sin cambiar filas.

Para cada tabla de escritura manual (`clientes`, `eventos_auditoria`, `citas`, `eventos_cita`, `intentos_cita_manual`) se ejecuta primero el SQL y luego se lanza un error. El rollback conserva la fotografía completa previa, incluido el intento preparado. Reintentar crea exactamente un cliente, cita, evento y auditoría; repetir después devuelve 200 con las mismas filas. La regresión de movimiento T086 vuelve a verificar rollback del horario y su evento. La regresión pública/privada T113 conserva apartados, reserva Pendiente, separación, cupo, idempotencia y las cinco rutas privadas del motor.
