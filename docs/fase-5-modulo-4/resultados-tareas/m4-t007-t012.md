## Flujo de migración y uso previsto

1. El ejecutor de pruebas exige `NODE_ENV=test` y `TEST_DB_*` confirmadas, crea una base `citas_m4_test_<UUID>` y aplica las migraciones mediante el DataSource existente; el descubrimiento por directorio ya incorpora los seis archivos en orden. No se ejecutó `migration:run` sobre la base cotidiana.
2. T007 y T008 agregan versiones mediante DEFAULT 1. Los escritores actuales pueden seguir insertando sin enviar ese campo; `synchronize` y `migrationsRun` automáticos permanecen desactivados. El incremento con cambios reales y la comparación de una versión observada pertenecen a tareas posteriores.
3. T009 prepara la persistencia del futuro envío manual. `clave` usa `ascii_bin`, entre 16 y 64 caracteres, sin espacios exteriores, y es única por negocio y cuenta. `contenido_hash` guarda 64 caracteres hexadecimales, sin cuerpo del formulario. Un intento preparado no tiene cita ni fecha de resolución; registrado exige ambas; no registrado exige resolución y no admite cita. Una cita no puede ser resultado de dos intentos manuales.
4. T010 permite agregar un evento por versión de cita. Exige exactamente una identidad: `actor_usuario_id` del personal o `sesion_publica_id`; la identidad pública solo admite acción `alta`. Las acciones previstas son alta, cambio de estado, cancelación, reactivación y cambio de horario. `valores_antes` es anulable, `valores_despues` obligatorio y ambos son JSON válido. El motivo opcional admite hasta 2.000 caracteres y no reutiliza notas de consulta.
5. La cita puede conservar varios eventos sin sobrescribirlos. La combinación negocio/cita/versión evita duplicados y los triggers rechazan editar o borrar un evento. Los servicios futuros deberán filtrar los valores operativos y excluir secretos antes de escribir JSON; esta tabla no acredita todavía ese filtrado ni autorización por rol.
6. T011 admite auditoría tipada de cliente. T012 cierra las referencias por `(negocio_id,id)`: una cuenta de Administración/Recepción no necesita perfil de Profesional, pero sí pertenecer al negocio. Cita y sesión también deben pertenecer a ese negocio. Las FKs no sustituyen la revalidación de permisos/licencia de las futuras operaciones.
7. En una instalación sin uso se puede revertir y volver a aplicar el lote. Con versiones modificadas, intentos, eventos, auditoría de cliente o referencias operativas utilizadas, sus down rechazan la pérdida de datos o garantías antes de modificar DDL. MariaDB no revierte ALTER/CREATE/DROP como DML: no se presenta una reversión de esquema como transacción atómica ni se recomienda borrar registros para forzarla.
8. El ejecutor cierra conexiones y elimina únicamente la base efímera que creó, incluso ante una aserción fallida. El SQL autónomo se prueba en otro esquema generado por el ejecutor de instalación, también eliminado al terminar.

La cuenta que aplica migraciones necesita permiso `TRIGGER`, además de los permisos DDL habituales. No se habilita escritura manual: las entidades de versiones y del modelo nuevo quedan para M4-T013/M4-T014 y su sincronización integral para M4-T015. El DDL canónico y el CHECK de la entidad existente sí se mantienen alineados en este lote por coherencia y regresión de instalación.

## Tests primero

`npm run test:integration -- --runInBand test/fase-5-t007-t012.integration-spec.ts`

Reveló otro conteo fijo en `sucursales-t060.integration-spec.ts`: al retirar solo diez migraciones ya no desmontaba ALA por completo. Se usa el mismo límite explícito que en las otras regresiones, sin cambiar servicios de sucursales ni rebajar aserciones.

Para aislar la verificación paralela, HTTP se lanza con un proceso Node que registra `ts-node` con `transpileOnly: true` y `rootDir: '.'` (requerido por TypeScript 6, sin modificar `tsconfig.json`), carga `test/setup-env.ts` y reutiliza `conBaseOperativa`. Dentro del callback abre el proceso hijo siguiente, con `TEST_DB_NAME` y `TEST_DB_CONFIRMED` iguales a `String(db.options.database)` y el resto de variables heredadas, sin imprimir sus valores:

```text
node --experimental-vm-modules node_modules/jest/bin/jest.js --config ./test/jest-e2e.json --runInBand
```

Es la suite HTTP completa sin filtros. El padre espera el resultado del hijo, propaga cualquier fallo y después cierra y elimina su base mediante el finally del ejecutor. Así la integración usa su configuración test habitual y HTTP su propia base ya migrada; las bases adicionales que creen los casos también son efímeras. No se escribieron archivos temporales de configuración ni se cambió `.env.test.local`.

Los mensajes de error inyectado que aparecen en consola HTTP pertenecen a casos aprobados de rollback y respuestas seguras; no son tests fallidos. La revisión final de formato y enlaces locales no encontró errores. El archivo incremental generado por build se devolvió a su contenido original para excluirlo del cambio.

## Cierre del lote

Los criterios propios de M4-T007–M4-T012 están cumplidos: las versiones se inicializan sin alterar datos anteriores, los intentos e historial representan el contrato, auditoría admite cliente sin abrir la lista de tipos, y las referencias/índices aíslan y acotan el modelo. Se marcan solo estas seis tareas, con sus once casos propios y regresión completa de integración/HTTP aprobadas. La suite unitaria global conserva el único fallo documental previo descrito; no se declara aprobada en su totalidad.
