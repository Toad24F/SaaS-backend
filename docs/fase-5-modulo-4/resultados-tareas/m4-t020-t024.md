## Flujo y contrato de uso

1. La entrada privada autentica el JWT por el mecanismo existente. La identidad que necesita este servicio contiene únicamente `sub` y `sesionId`; rol, negocio, estados y precios del navegador no son autoridad.
2. `ejecutar(identidad, permiso, callback)` abre `READ COMMITTED` y llama a `resolverEnTransaccion` antes de ejecutar el callback. Una operación nueva vuelve a leer el estado; no existe caché de autorización ni renovación deslizante de sesión.
3. El resolver exige transacción activa, identidad válida y uno de los seis permisos operativos. Captura el reloj inyectado una vez por resolución. Una única consulta une sesión, cuenta, negocio y licencia: la sesión debe pertenecer al usuario, no estar revocada, haber comenzado y no haber llegado a su vencimiento exacto. La proyección no selecciona el hash de contraseña.
4. Comprueba cuenta activa, no inhabilitada, activada y con nombre. Aplica la matriz según el rol leído de la base; Superadmin no recibe herencia operativa. Comprueba negocio activado y reutiliza `PoliticaAccesoLicenciaService`, sin reimplementar suspensión ni desplazar fechas. El Profesional debe tener su perfil en ese negocio.
5. Devuelve un contexto de servidor con manager, instante, actor, negocio, rol y perfil propio cuando corresponde. Sus propiedades de identidad y los filtros están congelados; el manager conserva sus funciones transaccionales. Una marca interna débil impide aceptar un objeto reconstruido desde JSON o usarlo con la transacción cerrada.
6. `alcanceCitas` obliga a filtrar por negocio y añade el perfil propio para Profesional. `alcanceClientes` exige además permiso de directorio y solo devuelve el negocio vigente. Los casos de uso posteriores deben combinar sus criterios validados sin sobrescribir estos límites; no reciben un negocio elegible desde el cliente.
7. Los futuros escritores deben adquirir sus bloqueos en el orden común y volver a llamar a `resolverEnTransaccion` con **el mismo manager después de esperar**. Este lote no sustituye la serialización por negocio/Profesional ni la revalidación del motor, cupo, oferta, horario o versión. La prueba con dos conexiones confirma que una revocación ya confirmada se observa en una nueva resolución `READ COMMITTED`.
8. La frontera de servicio normaliza fallos de apertura, resolución, callback y commit. El filtro HTTP optativo hace lo mismo con errores de guardas/controladores y no conserva mensajes arbitrarios aunque ya sean `HttpException`. Los futuros módulos HTTP importarán Auth y aplicarán este filtro; aquí solo el controlador de pruebas lo hace.

El resolver comprueba autoridad, no ofrece un calendario ni un listado paginado de producto. Tampoco convierte una lectura de permiso en reserva garantizada. Las consultas por rango, detalle, CRUD y escritores corresponden a las tareas posteriores.

## Clasificación de errores

| Estado | Mensaje seguro por defecto |
| --- | --- |
| 400 | Entrada operativa inválida. |
| 401 | Sesión no válida o acceso actual no disponible. |
| 403 | No tiene permiso para realizar esta operación. |
| 404 | Recurso no disponible. |
| 409 | La operación entra en conflicto con los datos vigentes. |
| 503 | No se pudo comprobar la operación. Reintente. |
| 500 | No se pudo completar la operación. Reintente. |

La excepción conocida de cupo conserva «No se puede registrar otra cita con este teléfono en esta sucursal. Contacta al negocio». Un error SQL genérico no se interpreta automáticamente como conflicto funcional. Los códigos de conexión, límite de conexiones, deadlock y espera de bloqueo previstos producen 503; lo inesperado, 500. No se devuelve lista vacía, resultado parcial ni `no_registrado` por un fallo técnico. No se registran nuevos logs con excepciones o formularios.

Se escribieron antes de implementar los componentes:


Primera ejecución: la matriz tuvo **13 fallidos y 12 aprobados** de 25, por permisos aún no concedidos. La suite de errores no pudo cargar el archivo todavía inexistente. Integración y HTTP también fallaron al cargar el servicio ausente (0 tests ejecutados, sin atribuirles cobertura).

Después de implementar: unitarias propias 41/41 e integración inicial 16/16 aprobadas. HTTP detectó que el módulo anfitrión de su controlador de prueba no importaba Auth para resolver `AuthModuleOptions`; se corrigió la composición de la prueba, sin sustituir guardas. Se añadió un caso de cuenta pendiente y comprobaciones de contextos cerrados/falsos: integración final 17/17, HTTP 4/4 aprobados. Las escrituras de esas pruebas usan solo bases `citas_m4_test_<UUID>` creadas y eliminadas por el ejecutor.

Antes del cierre se ampliaron dos tests existentes con roles `__proto__`/`constructor`/`toString` y estados HTTP de tipos o valores inválidos. La ejecución enfocada (`-t 'desconocidos|distingue'`) falló en ambos: un rol heredado causaba TypeError y el estado `'500'` conservaba tipo string. Se corrigieron después mediante claves propias de la matriz y validación numérica del estado. La repetición completa de las dos suites propias aprobó 41/41; no aumentó el número de casos porque se añadieron aserciones a tests existentes.

## Límites del lote

Se verificaron enlaces locales de esta evidencia, matriz y tareas, y `git diff --check` sin errores. Se marcan exclusivamente M4-T020–M4-T024 y se detiene el trabajo en ese límite.

La evidencia corresponde a permisos, contexto, alcance y errores seguros. Las rutas operativas de agenda/clientes, sus filtros/paginación y escritores reales siguen pendientes de M4-T025 en adelante. No se cierra ningún RF completo de gestión por autorizar su futura operación, ni la fase, ni M3-T136 o las integraciones manuales M2-I004/M3-I001 y ALA-I001–ALA-I003. Los contratos y cinco rutas privadas de disponibilidad y el escritor público se conservan.
