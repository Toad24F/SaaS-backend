## Flujo y contrato HTTP

Todas las rutas exigen JWT y permiso `CREAR_CITA_MANUAL`: Administración o Recepción del negocio actual. El servicio relee sesión, cuenta, rol, negocio y licencia desde la base; los claims incorrectos del JWT de prueba no conceden autoridad. Las respuestas, incluidos errores, llevan `Cache-Control: no-store`.

| Ruta POST | Cuerpo | Resultado |
| --- | --- | --- |
| `/citas/manuales/intentos` | `{clave, seleccion}` | 201 con proyección del intento preparado o ya registrado; repetir preparación conserva la fila. |
| `/citas/manuales/intentos/:clave/registrar` | La misma selección | 201 con la cita nueva; 200 con la misma cita/folio al repetir. |
| `/citas/manuales/intentos/:clave/resolver` | La misma selección | 200 con `{estado:'registrado', resultado}` o `{estado:'no_registrado'}`, una vez confirmado su resultado durable. |

La selección admite `clienteId` **o** `clienteNuevo:{nombreCompleto,telefono}`, más `sucursalId`, `personalId`, `servicioId`, `fechaLocal`, `horaInicio` y `notas` opcionales. La clave opaca estable de 16–64 caracteres la conserva el solicitante antes de preparar; permite resolver incluso si la respuesta de preparación se perdió. Campos desconocidos, precio, negocio o fines calculados son inválidos. Preparar no ocupa ni promete el horario.

1. Validar clave y selección y calcular la misma huella HMAC canónica del registro. El intento no almacena contacto ni notas.
2. Abrir `READ COMMITTED`, comprobar acceso, bloquear la fila del actor y después leer con `FOR UPDATE` únicamente el intento de ese negocio/actor/clave. El actor serializa incluso cuando aún no existe fila; no se usa una ausencia simple como prueba de fracaso.
3. Después de esperar, releer acceso y capturar el instante del reloj inyectado. Una huella distinta recibe 409 sin alterar el intento.
4. Si está `registrado`, consultar su cita por negocio e ID persistido y devolver su snapshot. No ejecutar motor, cupo, alta de persona, cita ni evento adicionales. Un resultado incoherente sigue siendo fallo técnico.
5. Si está `preparado`, actualizarlo a `no_registrado` con el instante de resolución. Si todavía no existe, insertar directamente una fila terminal con clave y huella bajo el bloqueo del actor. Si ya era terminal, devolverlo sin renovar fechas.
6. Confirmar antes de responder ausencia. Una preparación o registro posterior con esa misma clave recibe 409: no resucita la operación. Para un nuevo envío conocido como no registrado se necesita otra clave.

Si gana el escritor, el resolutor espera y devuelve la misma cita después del commit. Si gana el resolutor, el escritor espera y observa el cierre terminal. Si no puede adquirir el bloqueo o determinar el resultado, responde 503; un error inesperado responde 500. Ninguno autoriza a iniciar otra reserva interpretándolo como ausencia. Otro actor con igual clave resuelve su propio espacio de intentos y nunca obtiene la cita ajena. La recuperación privada sigue exigiendo acceso/licencia vigentes.

## Tests primero y evidencia por tarea

Antes de implementar, los cuatro tests HTTP fallaron: rutas inexistentes (404) y método `resolver` ausente. Los cuatro casos iniciales de integración también fallaron por ese método ausente. Tras implementar, la primera ejecución pasó 21/21 tests de integración (cuatro nuevos más los 17 previos) y 4/4 HTTP. Después se añadieron los casos de timeout real y recuperación/acceso para reforzar T059.

La primera ejecución dentro del sandbox no pudo conectar a MariaDB (`EACCES`); se repitió con acceso local permitido para obtener el rojo funcional anterior. La suite unitaria también necesitó acceso a sus servidores HTTP locales: dentro del sandbox tuvo tres fallos `EACCES` y 577 aprobados; el resultado definitivo se registra en verificaciones.

| Tarea | Pruebas y observaciones |
| --- | --- |
| M4-T059 | Dos instancias Nest/DataSource, barrera después del `FOR UPDATE` real y conexión rival observada en `PROCESSLIST` esperando sobre usuarios. En orden escritor primero, ambos devuelven la misma cita y solo se añade una persona/cita/evento. Un bloqueo externo con `innodb_lock_wait_timeout=1` causa 503 real y deja todas las filas previas intactas; liberarlo permite resolver. |
| M4-T060 | Cierre con y sin preparación, repetición estable sin renovar fechas, huella distinta rechazada, preparación y registro tardíos rechazados. En orden resolutor primero, el registro rival recibe 409 y ninguna persona/cita/evento se añade. Se persiste solo la fila terminal, sin contacto ni notas. |
| M4-T061 | Se ejecutan nuevamente los cinco casos reales de rollback de `test/fase-5-t053-t058.integration-spec.ts`. Inyectan fallo **después** del SQL de cliente, auditoría de cliente, cita, evento de cita y actualización de intento. Comparan completas las cinco tablas con el estado anterior; restaurada la instrumentación, la misma clave preparada crea una sola cita y un evento. No se duplica esa cobertura en un archivo nuevo. |
| M4-T062 | HTTP real con JWT de Administración y Recepción: preparación, creación 201, repetición 200 y resolución del mismo resultado; actor/negocio proceden de base aun con claims falsos. Comprueba 400, 401, 403, 404 y 409, `no-store`, ausencia terminal, otro actor, campos desconocidos y errores 500/503 sin SQL/trazas. Los dos últimos errores se inyectan en el servicio para comprobar la frontera HTTP; el timeout SQL real se acredita por separado en T059. |

La recuperación histórica desactiva y cambia el costo del servicio después de registrar; resolver conserva exactamente el resultado anterior, no llama motor/cupo ni modifica filas. La revocación posterior impide recuperar con 401. Los espías de carreras delegan SQL real; el escritor y resolutor no se sustituyen por dobles.

Las pruebas de persistencia usan exclusivamente bases `citas_m4_test_<UUID>` creadas/migradas/eliminadas por `conBaseOperativa`, con reloj controlado y limpieza en `finally`. La base cotidiana no se usa para escrituras.
