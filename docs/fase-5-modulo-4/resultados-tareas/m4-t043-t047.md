## Contrato HTTP

| Ruta | Entrada y resultado |
| --- | --- |
| `GET /clientes` | `busqueda`, `pagina`, `limite`; 200 con `{clientes,pagina,limite,hayMas}`. |
| `GET /clientes/:id` | ID explícito, sin query adicional; 200 con la ficha y su versión. |
| `GET /clientes/:id/citas` | ID explícito y paginación; 200 con `{citas,pagina,limite,hayMas}` y snapshots históricos. |
| `POST /clientes` | `nombreCompleto` y `telefono`; 201 con ficha nueva, versión 1, sin crear cita. |
| `PATCH /clientes/:id` | `version` numérica obligatoria y nombre y/o teléfono; 200 con ficha vigente, 409 para versión antigua. |

Se conservan los validadores del lote anterior: teléfono mexicano normalizado a diez dígitos; nombre no vacío de hasta 150 caracteres; búsqueda literal, paginación acotada e IDs decimales positivos. Los objetos de entrada admiten solo los campos previstos. Administración y Recepción operan sobre su negocio persistido; Profesional y Superadmin reciben 403. Una petición sin sesión recibe 401. ID ajeno e inexistente devuelven el mismo 404 seguro; errores temporales e inesperados se distinguen mediante 503/500. Las respuestas personales, incluidos errores de guardas y servicio, llevan `no-store`.

## Flujo del directorio

1. El controlador autentica el JWT; no toma el rol o negocio declarado en él como autoridad suficiente.
2. El servicio valida la entrada y abre su transacción existente; el acceso operativo reconstruye sesión, rol, negocio y licencia actuales en servidor.
3. Lista y ficha aplican alcance por negocio. Historial exige primero la ficha propia y consulta citas por negocio e ID de cliente, nunca por teléfono.
4. Alta siempre crea una persona independiente. Corrección usa los bloqueos y la versión observada del dominio existente; ficha y auditoría se confirman juntas. Las citas previas no se actualizan.
5. El controlador devuelve la proyección permitida; ante fallos, el filtro operativo devuelve un mensaje seguro y evita caché. Un fallo nunca se presenta como lista vacía.

## Flujo de elección explícita para uso interno

`resolverExistenteEnTransaccion(manager, identidad, clienteId)` exige un ID válido y una transacción activa. Revalida sesión, rol, licencia y permiso `CREAR_CITA_MANUAL` con ese manager y luego lee la ficha por negocio e ID. Dos fichas con el mismo teléfono producen resultados distintos según el ID. Un ID ajeno o ausente se rechaza, aunque exista una ficha propia con idéntico teléfono. No acepta búsqueda por teléfono como sustituto de la selección.

Este método no abre otra transacción ni escribe una cita. El futuro escritor deberá invocarlo tras sus bloqueos y revalidaciones, bajo el orden común, para guardar contacto y cita en su propio commit. Aquí no se acredita esa integración ni se adelantan M4-T048/M4-T054.
