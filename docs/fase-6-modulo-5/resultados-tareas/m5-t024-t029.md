# Resultado M5-T024–T029 — unión de clientes e identidad activa

Fecha: 22 de noviembre de 2026. T024–T026 y T029 corresponden a la interfaz del repositorio `frontend-saas`; T027–T028 se implementaron aquí con autorización expresa para este lote. Las pruebas SQL usan únicamente las bases efímeras que crea y elimina `conBaseMigrada`/`conAgendaHttp`; no se ejecutó una migración sobre la base cotidiana.

## Flujo implementado

1. Al corregir una ficha, `PATCH /clientes/:id` puede responder 409 `cliente_coincidente` con destino mínimo. La interfaz muestra ese destino y el efecto sobre los historiales. Volver a editar no envía una unión ni cambia las fichas.
2. Aceptar construye una sola vez `{destinoId, versionOrigen, versionDestino, clave, datosPropuestos}` y guarda la misma entrada en `sessionStorage` antes de `POST /clientes/:id/uniones`. Un doble clic no envía otra operación. Una respuesta perdida conserva el intento; el mismo panel o el aviso del directorio tras recargar lo repite literalmente. Una respuesta confirmada abre la ficha destino y su historial.
3. Para duplicados heredados, «Revisar coincidencias» recorre el directorio autorizado, compara nombre normalizado y teléfono y muestra cada posible destino. El usuario elige uno; la unión se envía sin `datosPropuestos`. El servidor vuelve a comprobar negocio, permiso, identidad y versiones y mueve solo los vínculos de citas. Los snapshots históricos permanecen iguales.
4. La migración final exige primero que no existan fichas activas sin clave ni grupos activos repetidos. Luego crea `nombre_activo` calculado: conserva `nombre_normalizado` para una ficha activa y vale `NULL` para una absorbida. El índice único `(negocio_id,nombre_activo,telefono)` impide duplicados activos con comparación binaria. Una actualización con duplicados se detiene antes del DDL para permitir conciliarlos.

## Pruebas y resultados

- **Pruebas primero:** la nueva prueba Node del frontend falló por módulo ausente; la de navegador falló porque aún no había advertencia; la integración SQL falló por migración ausente. Se implementó después de registrar esos fallos.
- `npm run test:integration -- --runInBand test/fase-6-t009-t013.integration-spec.ts test/fase-6-t014-t017.integration-spec.ts test/fase-6-t018-t023.integration-spec.ts test/fase-6-t027-t028.integration-spec.ts`: **4 suites, 23/23 pruebas aprobadas**. Comprueban unión HTTP, permisos, rollback, carreras anteriores y DDL final.
- La regresión de seis suites de semillas SQL dio inicialmente **47/48** por una inserción antigua sin clave normalizada; se corrigió y `test/fase-3-t005-t010.integration-spec.ts` pasó **3/3** al repetirse. Las otras cinco suites habían pasado en la corrida conjunta.
- `npm run build`, `npm run lint` y `git diff --check`: aprobados.
- `npm test -- --runInBand` con puertos locales autorizados: **101/102 suites y 661/662 pruebas aprobadas**. El único fallo es el caso documental previo `test/fase-5-t122-t124.spec.ts`, que exige archivos ausentes del frontend según la evidencia de M5-T001–T007. No cubre unión ni migraciones. La corrida inicial dentro del sandbox añadió tres fallos de puerto `EACCES`; al repetirla con acceso local quedaron resueltos.
- Frontend: `npm test` **300/300**, navegador de Clientes **24/24**, `npm run build` y `git diff --check` aprobados. El navegador usó respuestas HTTP interceptadas; no acredita por sí solo una sesión contra API real.
