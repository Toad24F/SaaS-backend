# M5-T059–T062 — Persistencia de WhatsApp

## Qué se realizó y flujo

Este lote prepara las cuatro piezas durables del canal. Todavía no envía mensajes ni acepta webhooks: el transporte, los trabajadores y la confirmación operativa pertenecen a tareas posteriores.

1. `canales_whatsapp` admite un solo remitente por negocio. Guarda su ID externo, estado, versión y una referencia `secret://...` al gestor de secretos; no contiene token ni credencial utilizable. El canal nace deshabilitado.
2. `envios_whatsapp` almacena un efecto por negocio/cita/generación/tipo y una clave única de efecto. La FK compuesta exige una condición de esa cita y negocio. Conserva destino, parámetros mínimos de plantilla, programación, límite de utilidad, estado, intentos, próximo intento, lease y referencias/horas de entrega. Un trabajo `en_proceso` exige ID y vencimiento de lease; los demás estados no los admiten. Los índices permiten buscar trabajo y consultar el historial de la cita. El destino y los parámetros son datos operativos sensibles: los futuros escritores deben limitar su contenido y no incluir notas clínicas.
3. `eventos_whatsapp` recibe una huella estable única por negocio, tipo, ID de mensaje, hora de recepción del servidor y hora declarada por el proveedor por separado. Conserva hashes opcionales de remitente y acción, no el cuerpo completo del webhook ni un payload de confirmación utilizable. La repetición de la misma huella no crea otra fila.
4. `acciones_confirmacion` conserva únicamente el hash del token, vencimiento y consumo. Una FK compuesta la une al envío, cita, generación y negocio exactos. El tipo fijo de envío impide crear acciones sobre recordatorios o mensajes de citas ya confirmadas. El token utilizable se generará fuera de la base en una tarea posterior.

## Pruebas y resultados

Se escribieron primero cuatro pruebas de integración: fallaron por ausencia de las tablas. Se añadió después el caso que vincula una acción a un recordatorio: falló antes de la FK y pasó tras restringirla. La prueba de actualización desde T058 verifica que las citas existentes no cambian y no se crean filas de comunicación retroactivas.

- Integración T059–T062: **5/5**. Cubre canal único, referencia de secreto, efecto único, generación/negocio, lease, índices, evento duplicado, horas distintas, hash, consumo, cruce de IDs y prohibición de acciones sobre recordatorios.
- Instalación/actualización existente: **2/2**.
- HTTP de regresión de arranque: **4/4**.
- `npm run build`, `npm run lint` y `git diff --check`: correctos.
- Suite unitaria completa: **664/665** pruebas y **102/103** suites. La prueba documental `test/fase-5-t122-t124.spec.ts` sigue fallando por su referencia local de fase 5, observada también antes de este lote.

Las pruebas con escritura usaron exclusivamente bases desechables `citas_m4_test_*`. No se ejecutó un envío real, un webhook real ni un cambio de frontend; las tablas no acreditan por sí solas esas capacidades.
