# M5-T079–T083 · Reintentos, recuperación y acuses de WhatsApp

## Flujo

1. Un rechazo transitorio conocido libera la toma y vuelve a programar el mismo envío. Después del primer intento espera al menos un minuto y, después del segundo, al menos cinco minutos. Si Meta pide más tiempo, se usa su espera. Al alcanzar tres intentos, perder utilidad o recibir un rechazo permanente, queda `fallido`. Para un mensaje inicial Pendiente, el fallo terminal deriva a seguimiento manual solo si la condición sigue vigente. El estado y la versión de la cita se conservan.
2. Antes del HTTP, la transacción confirma el contador, la marca de inicio y un UUID del intento. El adaptador envía el UUID como `biz_opaque_callback_data`. Un resultado ambiguo o una toma vencida después de marcar el inicio deja `incierto`. Ambas rutas conservan el UUID y excluyen el envío de nuevas tomas de transporte. Si Meta devuelve el UUID en un acuse firmado, se puede asociar su ID de mensaje aun cuando la respuesta original del POST se haya perdido. Los envíos anteriores con un ID ya conocido se correlacionan por ese ID dentro del mismo negocio.
3. `GET /webhooks/whatsapp` valida modo, token y reto antes de devolver el reto como texto plano. Para `POST /webhooks/whatsapp`, Express captura hasta 3 MiB en bytes originales y rechaza compresión. El controlador compara la firma HMAC-SHA256 en tiempo constante antes de decodificar el JSON. El negocio se obtiene del `metadata.phone_number_id` firmado y su canal registrado, incluso si el canal está deshabilitado para envíos. Una notificación de un remitente no registrado se acusa sin escritura. [Verificación y firma de Meta](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/) · [Contrato HTTP del módulo](contratos-http-t005.md).
4. Se guarda un recibo mínimo por evento en `READ COMMITTED`. La huella distingue tipo, ID y hora de Meta para estados e ID entrante para botones. La clave única por negocio deduplica entregas simultáneas. Para botones se guardan el ID del mensaje, el contexto y las huellas de acción y remitente. El cuerpo original y los valores utilizables de la acción quedan fuera de la persistencia. Un fallo de inserción devuelve 503 y revierte la bandeja de ese lote.
5. Después del commit de recepción, cada acuse de estado se aplica en otra transacción. Al repetir un POST, los recibos ya procesados se conservan y los pendientes se retoman. El estado puede avanzar a `aceptado`, `entregado` o `leido`. Un acuse atrasado de menor avance puede completar su hito y conserva el estado más avanzado. Se guarda por separado la hora declarada por Meta y la primera recepción del servidor para cada hito. Un fallo de entrega previo a cualquier evidencia de entrega deriva la condición vigente a seguimiento. Una entrega posterior actualiza la comunicación y conserva el seguimiento. Las respuestas rápidas quedan en la bandeja para las tareas M5-T084–T085.

## Configuración

El despliegue suministra `WHATSAPP_WEBHOOK_APP_SECRET` y `WHATSAPP_WEBHOOK_VERIFY_TOKEN` desde el entorno. La primera variable verifica la firma y protege la huella del número remitente con HMAC y el prefijo `remitente-whatsapp:`. El UUID de correlación es independiente del token del arrendamiento. Se genera uno nuevo por intento y se retira al cerrar un rechazo conocido.
